Pidgin: runtime-learned binary encoding for JSON APIs

Learns the schema of your JSON responses, drops the keys and writes the values in a compact binary form. No .proto files, no code generation. Early: the Python library, the FastAPI and Django middleware and the JavaScript decoder work; most web server modules do not yet.

pip install pidgin-codec

Features

Two layers, each useful independently.

core

SchemaCodec

Runtime-learned binary encoding. Give it sample JSON and it infers the schema: field names, types, enum values, nesting. It then drops the keys and writes each value with an encoder for its type. Every payload is checked to decode back to the same data; data that does not fit the profile is refused, so it can be sent as JSON.

optional

RatchetCipher

Forward-secrecy encryption for persistent channels (WebSocket, SSE, IoT). The key moves forward after every message, so a key taken later cannot decrypt earlier messages. Install with pip install "pidgin-codec[crypto]".

SchemaCodec

from pidgin import SchemaCodec

# Learn schema from sample records
codec = SchemaCodec.learn(sample_records)

# Compress: 10-19% of the JSON on generated data, about brotli on real APIs
compressed = codec.compress(records)

# Decompress: the same data back
original = codec.decompress(compressed)

Schema Evolution

# v1 schema
codec_v1 = SchemaCodec.learn(users_v1)

# Data gains new fields
profile_v2 = codec_v1.profile.evolve(users_v2)
codec_v2 = SchemaCodec(profile_v2)

# v2 encodes and decodes both old and new data shapes
codec_v2.compress(old_data)  # missing new fields → absent marker
codec_v2.compress(new_data)  # new fields encoded as typed values

How It Works

Two stages. Each can be used on its own.

JSON Input
Raw structured data (list of dicts)
|
SchemaCodec
Learn schema from samples. Strip all keys.
Encode values by inferred type (int, float, str, bool, enum, nested).
Apply brotli on top. Output: compact binary.
|
RatchetCipher (optional)
Forward-secrecy encryption for persistent channels.
Key ratchets after every message.
Past messages safe even if future key leaks.
|
Wire Output
Compressed, optionally encrypted binary

Where Pidgin helps and where it does not

Generic compressors (gzip, brotli, zstd) treat data as opaque byte streams. They find repeated byte patterns but cannot exploit structural knowledge. In a JSON array of 1000 objects, the key "email" appears 1000 times. Generic compressors reduce this to a few bytes with backreferences; Pidgin leaves it out, because the key is in the profile and each record holds only values in a fixed order. With type-specific encoding (varints for integers, enum indices for repeated strings, sub-profiles for nested objects) this gives smaller output on responses with many fields. On text-heavy responses or ones with few fields brotli is as good or better.

The server modules are built on libpidgin, a C library. The middleware learns from the first 30 records per endpoint, encodes for clients that send Accept-Encoding: pidgin and serves profiles at /.well-known/pidgin/. Pagination wrappers such as {"data": [...]} are sent as plain JSON.

Schema Evolution

What happens when the API changes.

API ChangeWhat Happens
New field addedWritten as JSON inside the payload until the profile evolves, then typed
Field becomes optionalThe evolved profile marks it nullable; absent costs one byte. Before that, records without it are sent as JSON
New enum valueAppended; old indices keep their meaning
Int becomes floatWidened
Schema drift in the middlewareEvery 500 requests the keys are compared; if they changed, the profile evolves and gets a new version and ETag

A payload decodes only with the profile version it was encoded with. Clients should fetch the profile again when the X-Pidgin-ETag header changes.
